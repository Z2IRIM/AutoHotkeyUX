## 业务语义和决策

- 按前文将后续“转译”理解为已有 AHK 转成可视化流程；本阶段可视化创建仍需生成 AHK，才能使用现有解释器执行。此方向解释已在进度和设计中说明。
- 第一阶段采用原生 WinUI 动作卡片，复用现有目录、进程和启动服务，不增设第二套执行器。六类动作适用于常见自动化，触发器支持快捷键和脚本启动时。
- 当前窗口条件作用于整条流程；完整分支/循环、自由代码块和任意代码反向解析不进入本 Gate。界面不会把有限的窗口条件能力描述为完整图形语言。
- 流程数据作为编辑依据，生成代码保存哈希用于手工修改保护。两份文件保存需考虑失败恢复，不承诺普通双文件写入具有原子性。
- 预览的 Create script 只展示预览结果，不写文件或执行动作。正式实现创建与运行分离，运行仍由现有 Run/Restart 明确触发。
- 创建流程使用卡片、参数表单和默认折叠的生成代码；提供排序和撤销，不要求用户编写 AHK。

## 验证与实际结果

1. 使用 visualize 的 `scripts/render.py <fragment> .verification/visual-creation/preview.html` 渲染独立沙盒预览，读取原文件确认是真实片段而非转义字符串。
2. `node .verification/visual-creation/check-preview.cjs`：真实独立无界面 Edge 检查通过。覆盖初始草稿/代码、添加和文本转义、按钮排序、撤销/重做、无效 URL 阻止创建、条件与两种触发、创建结果预览、亮色/暗色，以及 1080/736/390/320 像素视口。各宽度无控件越界或横向溢出，页面异常为空。报告 `preview-report.json`。
3. `AutoHotkey64.exe /ErrorStdOut=UTF-8 <isolated-fixture>`：启动触发、条件快捷键、六类动作的三份生成样本，真实 v2 语法解析退出码均为 0。每份文件开头有 `ExitApp 0`，不会执行预览动作。报告 `syntax-report.json`。
4. 已实际查看宽/窄截图，布局符合当前产品的 WinUI 风格，窄窗口参数区域移到流程下方。

首次浏览器检查在 Windows 沙盒启动阶段卡住，尚未进入页面；按本次检查的 PID/命令行和专用 profile 核对后，仅终止其进程，在独立检查进程中完成上述验证。此项属于检查环境问题，不记作产品功能失败。

首次 PowerShell 直接调用 GUI 解释器未等待退出，得到空退出码，因此没有作为通过证据；改用 Hidden + Wait + PassThru 后获取三份真实退出码。
